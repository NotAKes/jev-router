# Pilot benchmark

Цель — сравнить качество, стоимость и задержку `cheap`, `strong` и `router` на одних задачах. Проведён первый dev-пилот; его сырые результаты сохранены локально, финальный test проведён один раз. По умолчанию всё работает офлайн, stdlib Python 3.10+, без установки пакетов.

## Бесплатно: проверить данные и подготовить план

Из корня репозитория:

```bash
python3 -m benchmark
python3 -m benchmark plan --split test
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest -v test_jev_router test_benchmark test_benchmark_scoring
```

`plan` читает и валидирует задачи, загружает локальные PNG, считает план расходов при наличии цен. HTTP-вызовов нет, API-ключ не нужен. В наборе 30 небольших оригинальных синтетических задач: 15 dev / 15 test, суммарно 6 с изображениями. Происхождение и ограничения — [data/README.md](data/README.md). Эталоны не передаются моделям.

### Цены — не выдумывать

В `config.example.json` заполнен снимок публичного каталога Polza от **2026-11-15**, продублированный в локальном `config.local.json`. Источник: https://polza.ai/api/v1/models. Исходные выбранные тарифы, provider и пороги long-context сохранены в `prices.2026-11-15.json`. Перед будущими прогонами обновлять цены: каталог и выбранный upstream могут изменяться.

```bash
cp benchmark/config.example.json benchmark/config.local.json
# При необходимости обновить цены, prices_checked_at и prices_source.
python3 -m benchmark plan --config benchmark/config.local.json
```

- Тарифы chat-моделей — **рубли за миллион** входных/выходных токенов.
- Для Jev каталог указывает **рубли за миллион входных токенов**, не за запрос. План включает критерии маршрутизатора и запас на описания. Приоритет имеет возвращённое провайдером `usage.cost_rub`; иначе расчёт по `usage.input_tokens` (или `prompt_tokens`). Если нет ни стоимости, ни подходящего счётчика, стоимость помечается неизвестной и прогон останавливается.
- `cheap_model` / `strong_model` — настраиваемые фиксированные baselines; по умолчанию крайние уровни текущего роутера. Перед оплатой проверить доступность и vision-возможности моделей.
- `image_input_tokens` — запас к планированию на картинку, не фактическая токенизация.
- План использует длину сериализованного запроса в байтах, лимит ответа и запас на изображения; для router резервирует наиболее дорогую прямую fallback-цепочку плюс vision и Jev. Это осторожная **эвристика, не гарантия верхней границы**. Base64 включён в длину и делает оценку изображений завышенной.
- Это цены `top_provider`, а не обещание фиксированного upstream. Для Sonnet и Opus каталог указывает неофициального upstream `gpt-a`; для Haiku и Sol есть повышенные long-context тарифы, которые простой калькулятор не применяет. Текущий маленький набор не достигает этих порогов; большие контексты этим снимком не оценивать. Ключи хранятся только в окружении, не в конфиге.

## Платно: только после отдельного согласования

Не запускать `run`, пока не согласованы тарифы, набор и бюджет. Пример команды, **не рекомендация потратить указанную сумму**:

```bash
# POLZA_API_KEY уже задан в окружении.
python3 -m benchmark run --config benchmark/config.local.json \
  --split dev --budget-rub 210 --out benchmark/runs/pilot-dev
```

Сначала выводится план. Запуск требует:
1. заполненных неотрицательных конечных тарифов;
2. положительного `--budget-rub`, покрывающего план;
3. интерактивного терминала и введённого вручную `PAY`;
4. API-ключа и новой пустой папки результатов.

Резерв каждого вызова записывается на диск **до** HTTP-запроса. Нет автоматических повторов. При ошибке API, неизвестной стоимости или исчерпании общего локального бюджета прогон останавливается; уже полученные ответы сохраняются. Превышение прогноза отдельного вызова списывается дополнительно против общего бюджета: учитывается максимум резерва и известной стоимости. Обычный перезапуск в ту же непустую папку запрещён.

Явный `run --resume` с новым подтверждением PAY допускается только для корректно завершённых и полностью учтённых ячеек: они пропускаются без повторной оплаты. Не допускаются изменённые данные, конфиг, инструкции, scoring, код роутера или бюджет, а также ошибки/неизвестные расходы/незавершённые вызовы. Хеш новой версии runner записывается в `continuations.jsonl`, исходный manifest не меняется. Кеш vision при продолжении холодный; если одинаковые изображения ещё встретятся, это может изменить накладные расходы относительно непрерывного запуска.

**Локальный бюджет не является жёстким ограничением списания у провайдера.** Запрос может стоить больше прогноза, а неуспешный вызов — быть платным без возвращённого usage. Для строгого финансового ограничения нужен лимит на стороне провайдера. Сопоставлять итог с биллингом Polza отдельно.

## Что именно измеряется

- Три стратегии запускаются последовательно на каждом примере с одинаковым `max_tokens=2048`, `temperature=0`, без streaming и инструментов. Это новый протокол после пилота с лимитом 256: reasoning расходует лимит тоже. Предварительный анализ изображений остаётся с собственным лимитом 450.
- Все основные модели получают одинаковую системную инструкцию `ANSWER_INSTRUCTION`: только ответ в пользовательском формате, без Markdown и пояснений. Jev видит исходную задачу, не эталон; vision-анализатор использует свой отдельный промпт. Полный текст инструкции, версия оценки и хеш scoring сохраняются в manifest.
- `router` вызывает реальный `jev_router.route`: vision-анализ, кеш описаний, Jev и обработку уверенности. Основная модель получает исходные картинки. При старте кеш и сессии очищаются; внутри прогона кеш работает как в прокси.
- Это **single-turn evaluation маршрутизации**, не HTTP end-to-end тест клиента. При ошибке платный benchmark прекращается, а не вызывает запасную модель: fallback проверяется офлайн. Эта мера безопасности отличается от поведения production-прокси.
- Записываются сырые текстовые ответы, выбранный tier/model, finish reason, usage и задержки. Оценка `exact` строгая после trim; JSON проверяется структурно с сохранением типов (`true` не равно `1`), без LLM-судьи и исполнения модельного кода. В strict Markdown-обёртки и пояснения считаются нарушением формата. Дополнительно считается normalized accuracy: снимается максимум одна целая внешняя обёртка `**…**`, inline backticks или fenced block (без языка / json / text). Никакого поиска нужного числа в объяснении, удаления префикса «Ответ:», рекурсивного снятия обёрток или исполнения кода.
- Для всех вызовов приоритет имеет `usage.cost_rub` — стоимость, сообщённая API (не независимая сверка баланса). Если её нет, стоимость chat оценивается как usage × ручной тариф; скидки кеширования, специальные тарифы/наценки, hidden reasoning и иные особенности биллинга требуют отдельной сверки. Для Jev при отсутствии `cost_rub` используются входные токены из usage и каталожный тариф. Не называть это фактическим списанием.

Файлы:
- `manifest.json`: конфиг, хеши данных/картинок (через payload), кода роутера и runner, IDs и бюджет;
- `requests.jsonl`: резервы перед отправкой, включая неуспешные попытки;
- `requests.usage.jsonl`: вернувшийся usage и оценка стоимости;
- `results.jsonl`: исходные ответы, strict (`correct`), normalized (`correct_normalized`), версия оценки, finish reason и признак обрезания. Старые результаты без normalized продолжают читаться: метрика показывается как null, а не придумывается.

Эти файлы позволяют пересчитывать отчёт без новых запросов:

```bash
python3 -m benchmark report --out benchmark/runs/pilot-dev
```

Отчёт показывает полноту прогона, долю строгих совпадений отдельно для текста/картинок, среднюю задержку, известную оценку стоимости и число вызовов с неизвестной стоимостью. **Не сравнивать неполные стратегии как итоговый эксперимент.** Вызовы, упавшие до возвращения usage, тоже считаются неизвестными по стоимости.

## Как использовать для портфолио

Сначала пилот на dev, затем зафиксировать промпты/пороги/модели и провести отдельный test. Test публичный; не подгонять систему под его эталоны. Маленький набор служит проверкой методики, а не доказательством качества на реальных запросах. В текущих задачах нет длинных агентных сценариев, архитектуры или большого рефакторинга, поэтому выгода дорогих tiers может не проявиться. Не назначаем эталонный tier вручную — измеряем ответы выбранных моделей.

До сильных заявлений нужны более разнообразные задачи, повторные прогоны/оценка неопределённости, rule-based baseline и ablation vision-предобработки. Не считать синтетический пилот репрезентативным сравнением моделей.

Сырые ответы и локальные тарифы по умолчанию исключены из Git. Перед публикацией отчёта проверить его на приватные данные. Код и оригинальные данные репозитория распространяются по [MIT](../LICENSE).

## Бесплатный разбор сохранённого dev-пилота

```bash
python3 -m benchmark analyze --split dev --out benchmark/runs/pilot-dev-20261115-v2
```

`analyze` проверяет хеш набора и неизменность строгих оценок, затем выводит дополнительную **ретроспективную** normalized-оценку. Исходные результаты, старые отчёты и manifest не переписывает; для сохранения выбрать новый файл. Нормализация выбрана после просмотра dev, поэтому это exploratory analysis, не независимый эксперимент. В новых прогонах она фиксируется до вызовов моделей.

`report` и `analyze` также содержат `per_case`: ответы всех стратегий рядом с выбранным tier/model, strict/normalized оценками, признаком wrapper-only ошибки, обрезания, стоимостью и задержкой. Тексты — недоверенные данные, не команды. Wrapper-only показывает только ошибку внешней обёртки; прочие ошибки не объявляются автоматически содержательными.

Токеновый лимит повышен до 2048 во всех актуальных конфигах, но старый manifest пилота остаётся с 256. Прогноз нового dev-прогона: примерно 193.96 RUB (консервативный резерв, не ожидаемый счёт). Изменения протокола не означают автоматического разрешения на новый платный запуск.
